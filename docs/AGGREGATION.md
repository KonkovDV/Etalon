# База частот: запись вариантов и AN

В базе популяционных частот вариант — это ключ (CHROM, POS, REF, ALT), а частота — AC / AN. И ключ, и знаменатель зависят от того, как вызовы готовят к сборке. Здесь на тех же данных HG002 проверены два места, где одна и та же биология даёт разные числа: как записан вариант и кто входит в AN.

## Одна вариация — разные ключи

Три вызывателя работают на одном BAM: bcftools, Strelka2 и DeepVariant ([PRODUCTION](PRODUCTION.md)). Берутся их PASS-вызовы в доверенных участках GIAB v5.0q, ключи сравниваются на трёх уровнях: как есть, после разбиения мультиаллельных записей с обрезкой общих оснований и после сдвига инделов влево (`bcftools norm -m -any -f ref`). То, что и после этого различается, hap.py сравнивает по гаплотипам. В суперлокусах, которые hap.py засчитал целиком, гаплотипы собраны ещё раз из референса перебором фаз, уже без hap.py (`scripts/representation.py`).

### Что это значит для базы частот

Пока база собрана одним пайплайном с совместным генотипированием, запись внутри неё согласована. Расхождения появляются на стыках: при смене версии вызывателя, при объединении когорт, при сверке с gnomAD и другими базами, и когда вариант объявляют новым, потому что его ключа нет в чужой базе. На этих стыках нужен тот же порядок, что здесь:

1. `bcftools norm -m -any -f ref` для обеих сторон;
2. сверка оставшихся ключей по гаплотипам в окне (hap.py с движком vcfeval, vcfdist, Aardvark), а не по точному совпадению.

Сверка только по ключу завышает число новых вариантов и делит частоту одного варианта между несколькими записями.

## AN: у кого генотип известен

Если AN = 2 × число образцов, образец без данных в позиции молча считается гомозиготой по референсу, и частота занижается. gVCF даёт GQ для каждой позиции: у вызовов и у опорных блоков. Здесь генотип считается известным при GQ ≥ <!--ev:callable_gq_min-->20<!--/ev-->, как в gnomAD; неизвестный генотип не входит ни в AC, ни в AN. Данные — gVCF DeepVariant из серии по глубине ([METRICS](METRICS.md#f-и-глубина)), доверенные участки v5.0q.

### В схеме базы

`scripts/results_db.py ingest RUN --gvcf SAMPLE.g.vcf.gz` загружает уверенные интервалы gVCF в таблицу `callable`. Представление `v_allele_frequency` считает AF с AN = 2N, `v_allele_frequency_callable` — только по известным генотипам и показывает, у скольких образцов генотип неизвестен (`n_unknown`). Проверка — `tests/test_scripts.py`: у образца без данных и у вызова с GQ 8 генотип в частоту не входит.

Это модель на SQLite. На сотнях тысяч геномов тот же принцип реализуют разреженные форматы, которые хранят опорные блоки gVCF: gnomAD v4 объединяет gVCF в Hail, All of Us — в Genomic Variant Store, Genomics England в aggV3 — итеративным генотипированием gVCF в DRAGEN ([источники](LITERATURE.md#база-частот)).

## Границы

- Различия записи измерены на одном образце, участке 2 Мб и трёх вызывателях на одном BAM. На полном геноме в повторах и сегментных дупликациях таких локусов больше, и доля может быть другой.
- Когорта из копий одного генома — модель: в ней нет популяционной структуры, а разная глубина получена прореживанием, а не разными библиотеками.
- Всё посчитано в доверенных участках GIAB, где покрытие хорошее по построению. Вне их неизвестных генотипов больше.

## Как воспроизвести

```bash
make depth aggregation
```

`make depth` строит серию по глубине с gVCF DeepVariant, `make aggregation` сравнивает запись вызывателей на полной глубине и считает AN по gVCF.
