# Воспроизводимость

Цель: один и тот же вход даёт побайтно один и тот же VCF независимо от числа потоков, повторного запуска, движка CWL и пересборки образа. Побайтное совпадение — самый строгий и самый дешёвый критерий: один `sha256sum`, и не нужно спорить, «существенны ли» различия.

## Процессор: пять сборок bwa-mem2

bwa-mem2 поставляется пятью сборками под разные наборы инструкций: SSE4.1, SSE4.2, AVX, AVX2, AVX-512BW. Лаунчер `bwa-mem2` запускает лучшую из тех, что поддерживает процессор. Значит, на кластере с узлами разных поколений один и тот же образ выполняет разный машинный код, и одинаковый результат не гарантирован заранее.

Как проверено. На одном процессоре с AVX-512 каждая сборка запущена напрямую (вход workflow `bwa_simd`: `scripts/run_pipeline.sh bwa_simd=sse41`), и результат сравнен с прогоном через лаунчер. Процессор с AVX-512 умеет исполнять и все более старые наборы инструкций, поэтому так проверяются все пять веток кода. Сама сборка не зависит от того, на каком CPU она запущена: процессор лишь выбирает, какую из пяти сборок запустить.

BAM и VCF побайтно одинаковые у всех пяти сборок, так что узлы с любым x86-64 процессором от SSE4.1 и выше дают одинаковое выравнивание.

По дороге: если запустить сборку по её имени (`bwa-mem2.avx2 mem`), BAM отличается одной строкой заголовка `@PG CL`, потому что bwa-mem2 пишет туда `argv[0]`. Лаунчер передаёт сборке `argv[0] = bwa-mem2`, поэтому в CWL сборка запускается как `exec -a bwa-mem2 bwa-mem2.<сборка>` ([D-14](DEBUGGING.md#d-14)).

## Источники недетерминизма и что с каждым сделано

| Источник | Как проявляется | Что сделано | Чем проверено |
|---|---|---|---|
| bwa-mem2 оценивает размер вставки по пачке ридов, а пачка по умолчанию зависит от числа потоков | разные выравнивания при `-t 4` и `-t 2` | `-K 100000000`: пачка фиксирована в основаниях | BAM-записи 4 против 2 потоков совпадают |
| порядок ридов на входе | другие пачки — другие выравнивания | FASTQ строится детерминированно (`samtools collate` хеширует имена); fastp сохраняет порядок | выход fastp одинаковый при `-w 1/4/8` (MD5) |
| случайные каталоги cwltool `/var/lib/cwl/stg<uuid>/` | пути попадают в `##reference` VCF и `@PG` BAM | входы раскладываются в рабочий каталог шага и передаются по имени | VCF и BAM совпадают побайтно ([D-08](DEBUGGING.md#d-08)) |
| командные строки и версии в заголовках | `##bcftools_*Command`, `@PG samtools` | `--no-version` (bcftools), `--no-PG` (samtools) | `test_outputs_carry_no_run_specific_paths` |
| сжатие BGZF в несколько потоков | могло бы менять границы блоков | htslib делит поток на блоки BGZF до сжатия, поэтому число потоков не должно менять байты | косвенно: при одинаковом числе потоков BAM совпадает побайтно, при разном отличается только заголовок (`@PG -t N`), который сдвигает все блоки |
| версии программ | разные алгоритмы и значения по умолчанию | образ по digest; тарболы по sha256; apt по snapshot.debian.org | образ, пересобранный с нуля, дал тот же VCF |
| дата и время | `Date=` в заголовках | `--no-version` убирает строки с датой | побайтное сравнение |
| Монте-Карло в отчёте | интервалы F1 «плавают» | фиксированное зерно | `test_f1_interval_contains_point_estimate_and_is_deterministic` |
| пик длины вставки в отчёте fastp | fastp 1.4.0 считает его только в рабочем потоке 0, по каждой N-й пачке ридов | в отчётах не используется; патч для fastp ([D-23](DEBUGGING.md#d-23)) | с патчем гистограмма одинаковая при 1–4 потоках ([таблица](results/fastp_isize_threads.md)) |

## RNA-seq

Те же правила действуют для RNA-seq ([RNASEQ](RNASEQ.md#воспроизводимость)). При 4 и 2 потоках совпадают матрица счётов, таблица featureCounts, счёт STAR по генам, сплайс-сочленения, записи BAM и все числа отчёта; заголовок BAM отличается строкой `--runThreadN N`. При повторе на тех же потоках BAM совпадает побайтно.

Два источника недетерминизма здесь свои:

| Источник | Как проявляется | Что сделано | Чем проверено |
|---|---|---|---|
| STAR выбирает границы бинов сортировки по буферу потока, который заполнился первым | при повторе на тех же потоках другие байты BAM при тех же записях | BAM переписывается блоками htslib (`cwl/tools/bam-finalize.cwl`, [D-20](DEBUGGING.md#d-20)) | повтор на 4 потоках: BAM <!--ev:rnaseq_repro_same_threads_bam_bytes-->да<!--/ev--> |
| порядок записей с одинаковой позицией | мог бы зависеть от того, какой поток выровнял рид | не нужно: STAR сортирует по позиции и номеру рида во входе | 4 против 2 потоков: записи BAM <!--ev:rnaseq_repro_threads_4_vs_2_bam_records-->да<!--/ev--> |

## Что не проверено

- **Байты сжатых файлов на процессоре без AVX-512.** libdeflate, которым htslib сжимает BGZF, тоже выбирает реализацию по процессору во время работы. На CPU без AVX-512 побайтное совпадение сжатых BAM и VCF не проверялось. Записи VCF и выравнивания BAM от этого не зависят: их хеши считаются по распакованному тексту.
- **Другая архитектура.** Образ собран только для x86-64: у bwa-mem2 нет официальных бинарников для ARM.

## Как проверить самому

```bash
make repro
```

```bash
scripts/check_reproducibility.sh results/run_a results/run_b
```

Другая сборка bwa-mem2 (из `sse41`, `sse42`, `avx`, `avx2`, `avx512bw`):

```bash
scripts/run_pipeline.sh -o results/simd_sse41 bwa_simd=sse41
```

```bash
scripts/check_reproducibility.sh results/run results/simd_sse41
```

Код выхода 0 значит, что VCF, записи VCF, выравнивания BAM и итоги hap.py совпали. Отчёт пишется в `results/reproducibility.md`.
