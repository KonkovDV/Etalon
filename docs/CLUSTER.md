# Кластер: Slurm, Apptainer, Toil

Три способа запуска под Slurm, от простого к распределённому. Все три проверены на одноузловом Slurm 23.11 со slurmdbd (учёт через MariaDB) в тестовом контейнере, с Docker вместо Apptainer ([C-12](../CLAIMS_REGISTRY.md)). Итоги проверки — [results/slurm.md](results/slurm.md), учёт задач — [slurm_sacct.txt](results/slurm_sacct.txt).

| Скрипт | Что делает | Когда нужен |
|---|---|---|
| [`run_cwltool_apptainer.sbatch`](../slurm/run_cwltool_apptainer.sbatch) | весь пайплайн одной задачей на одном узле, cwltool + Apptainer | один образец, отладка, небольшие данные |
| [`run_toil_slurm.sbatch`](../slurm/run_toil_slurm.sbatch) | лёгкая задача-лидер Toil отправляет каждый шаг CWL отдельной задачей Slurm | большой образец: шаги идут на разных узлах с разными ресурсами, scatter параллелится |
| [`array_cohort.sbatch`](../slurm/array_cohort.sbatch) | массив задач: одна строка таблицы образцов — одна задача | когорта; падение одного образца не останавливает остальные |

## Почему Apptainer, а не Docker

На общих узлах HPC Docker обычно запрещён: демон работает от root. Apptainer запускает контейнер как обычный процесс пользователя. Есть и вторая причина, найденная при проверке ([D-10](DEBUGGING.md#d-10)): под Docker Slurm не видит ресурсы контейнеров. Контейнер — дочерний процесс `dockerd`, а не задачи, поэтому он вне её cgroup. В проверочном прогоне `sacct` показал MaxRSS 231 МБ и 4.5 CPU-с, хотя шаги внутри заняли до 1.1 ГБ и ~66 CPU-с. Значит, лимит `--mem` не защищал бы узел. Контейнер Apptainer живёт в cgroup задачи, и учёт Slurm с ним верен.

```bash
slurm/build_sif.sh   # один раз на узле с интернетом: образы -> .sif в общем каталоге
```

cwltool ищет `.sif` в `CWL_SINGULARITY_CACHE` по имени `<dockerPull с / → _>.sif`, поэтому вычислительным узлам интернет не нужен.

## Ресурсы: из замеров, а не на глаз

Каждый шаг CWL объявляет `ResourceRequirement` (`coresMin`, `ramMin`). Toil превращает их в `sbatch --cpus-per-task/--mem` для каждого шага. В проверочном прогоне `samtools sort` получил ровно 2.50G: формула `threads × 512 МБ + 512 МБ` из CWL. Значения `ramMin` сверены с измеренными пиками: в HTML-отчёте у каждого шага есть рекомендация `--mem` = пик × 1.5.

| Шаг | ramMin в CWL | Измеренный пик | Запас |
|---|---|---|---|
| fastp | 2048 МБ | 1138 МБ | 1.8× |
| bwa-mem2 mem | 4096 МБ | 559 МБ | 7× (на полном GRCh38 индекс займёт ~10–16 ГБ) |
| samtools sort | 2560 МБ | 237 МБ | рассчитан на `-m` × потоки при больших данных |
| hap.py | 4096 МБ | 365 МБ | на полном геноме hap.py требует несколько ГБ |

Запас для bwa-mem2 и hap.py оставлен намеренно: на мини-контиге пики малы, а на полном геноме нет.

## Задача-лидер Toil

```bash
sbatch slurm/run_toil_slurm.sbatch
```

- Лидеру нужен 1 CPU и 2 ГБ, но живёт он всё время работы пайплайна, поэтому ему нужен длинный `--time`.
- `TOIL_SLURM_ARGS="--partition=short --account=…"` добавляет флаги к каждой задаче-шагу.
- Каталог jobStore создаётся заранее (`mkdir -p .toil`), а venv с Toil должен быть в PATH задач, иначе `_toil_worker` не найдётся и задачи упадут с кодом 127 ([D-11](DEBUGGING.md#d-11)).
- `toil stats` после прогона даёт время и память по задачам — вторая независимая оценка рядом с `measure.py`.

## Когорта

```bash
N=$(($(wc -l < slurm/samples.tsv) - 1))
sbatch --array=1-${N}%20 slurm/array_cohort.sbatch slurm/samples.tsv
```

- `%20` ограничивает число одновременных задач, чтобы не перегрузить общее хранилище.
- Для образцов без эталона списки эталонов пустые: scatter hap.py пуст, отчёт без раздела точности, порог качества проверяет риды, картирование и Ti/Tv. Проверено: задача прошла, 5 из 5 проверок.
- Повторный запуск пропускает образцы, у которых уже есть VCF: массив можно перезапускать после сбоя.
- Каждый образец сразу загружается в `results/cohort/results.sqlite`.

## База результатов

`scripts/results_db.py` хранит прогоны, ресурсы шагов, точность по стратам и варианты в координатах GRCh38 в одной SQLite-базе. Ответ на вопрос о нескольких прогонах — один SQL-запрос:

```bash
python3 scripts/results_db.py query "SELECT run_id, threads, substr(vcf_sha256,1,12) AS vcf FROM runs"
```

```bash
python3 scripts/results_db.py query "SELECT grch38_pos, ref, alt, gt, dp FROM variants WHERE run_id='repro_t4' AND filter='PASS' AND grch38_pos BETWEEN 10637684 AND 10673999"
```

Первый запрос показывает, что VCF всех прогонов, кроме эксперимента с моделью инделов, одинаковы. Второй выдаёт варианты в гене *JAG1*: у HG002 их 50 PASS, 33 гомозиготных и 17 гетерозиготных. Представление `v_allele_frequency` считает AC/AN/AF по образцам, как популяционная база частот, только в малом масштабе ([db_summary.txt](results/db_summary.txt)).
