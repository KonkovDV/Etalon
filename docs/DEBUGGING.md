## D-01

**Где:** `make test` htslib 1.25 при сборке образа.
**Симптом:** 363 из 364 тестов, падает `ref-cache`: `Failed to open reference "http://localhost:1024/…": Input/output error`.
**Причина:** тест поднимает HTTP-сервер на localhost и читает референс через libcurl. В сборке был задан `http_proxy`, и libcurl отправил запрос к localhost в прокси.
**Исправление:** передавать `no_proxy=localhost,127.0.0.1` вместе с прокси. Это записано в комментарии `docker/tools/Dockerfile`, потому что сеть с TLS-инспекцией и обязательным прокси — обычное дело в медицинских организациях.
**Проверка:** чистая сборка `--no-cache --build-arg RUN_TESTS=1`, htslib <!--ev:htslib_tests_passed-->364<!--/ev--> из <!--ev:htslib_tests_total-->364<!--/ev-->.

## D-02

**Где:** `make test` samtools 1.25.
**Симптом:** `bash: line 1: bgzip: command not found`.
**Причина:** samtools собран против отдельно установленного htslib (`--with-htslib=/opt/hts`), а тест вызывает `bgzip` из PATH, где `/opt/hts/bin` ещё нет.
**Исправление:** `ENV PATH=/opt/hts/bin:${PATH}` в стадии builder до сборки samtools и bcftools.
**Проверка:** samtools <!--ev:samtools_tests_passed-->1020<!--/ev--> пройдено и <!--ev:samtools_tests_failed-->0<!--/ev--> упало (остальные — ожидаемые отказы самого набора тестов), bcftools <!--ev:bcftools_tests_passed-->2538<!--/ev--> из <!--ev:bcftools_tests_total-->2538<!--/ev-->.

## D-03

**Где:** релиз bwa-mem2 v2.3 (июнь 2025).
**Симптом:** `bwa-mem2 version` печатает `2.2.1`, а в `NEWS.md` архива последняя запись — 2.2.1.
**Причина:** в релизной сборке не обновили строку версии.
**Исправление:** версия закрепляется тегом релиза и sha256 архива, а не самоотчётом бинарника. В `TOOL_VERSIONS.tsv` и отчёт пишутся оба значения: «2.3 (release v2.3 tarball; binary self-reports 2.2.1)».
**Проверка:** `docker run hg002-mini/tools:1.0.0 cat /opt/hts/TOOL_VERSIONS.tsv`.

## D-04

**Где:** `cwl/tools/bwa-mem2-*.cwl`, `secondaryFiles`.
**Симптом:** `cwltool --validate`: `is not a dict. Expected a SecondaryFileSchema object`.
**Причина:** YAML читает `.0123` (суффикс индекса bwa-mem2) как число с плавающей точкой `0.0123`, а не как строку.
**Исправление:** кавычки: `".0123"`.
**Проверка:** все CWL-файлы проходят `cwltool --validate` (задание `lint:cwl` в CI).

## D-05

**Где:** fastp 1.4.0.
**Симптом:** шаг fastp идёт 40 с при 110 % CPU на 4 потоках, остальной пайплайн — 30 с.
**Расследование:** время не меняется ни от числа потоков (1/4/8), ни от сжатия выхода, ни от формата входа (BGZF или gzip), ни от оценки дубликатов. Отключение флагов по одному: без `--detect_adapter_for_pe` шаг идёт 2.1 с ([таблица](results/fastp_profile.txt)).
**Причина:** автоопределение адаптеров для парных ридов — отдельный однопоточный проход. Для парных ридов fastp и так обрезает адаптеры по перекрытию пары, поэтому флаг ничего не добавляет.
**Исправление:** флаг убран (`cwl/tools/fastp.cwl`). Тест `test_fastp_does_not_use_slow_adapter_autodetection` не даёт вернуть его.
**Проверка:** <!--ev:fastp_before_s-->39.6<!--/ev--> → <!--ev:fastp_after_s-->2.1<!--/ev--> с; число ридов с обрезанным адаптером и итоговые метрики hap.py те же. Выход fastp побайтно одинаковый при `-w 1/4/8`.

## D-06

**Где:** `scripts/make_report.py`, собственный код.
**Симптом:** доля дубликатов 21.5 % для PCR-free библиотеки, где fastp оценивает 5.75 %.
**Причина:** в JSON `samtools markdup` все счётчики — в ридах (`PAIRED` = риды из пар). Код делил `DUPLICATE PAIR` (риды) на `PAIRED // 2` (пары).
**Исправление:** доля = `DUPLICATE PAIR / PAIRED`. Оптические и библиотечные (ПЦР) дубликаты считаются отдельно: первые — свойство проточной ячейки, вторые — библиотеки.
**Проверка:** три независимых источника сходятся: `samtools stats` («reads duplicated» 55 122 из 513 406 = 10.7 %), markdup <!--ev:dup_rate_pct-->10.7<!--/ev--> %, из них оптических <!--ev:optical_dup_pct-->6.2<!--/ev--> % и библиотечных <!--ev:library_dup_pct-->4.6<!--/ev--> %; оценка fastp (5.75 %) близка к библиотечной доле.

## D-07

**Где:** `samtools stats` против `samtools coverage`.
**Симптом:** средняя глубина по гистограмме COV — 38.6x, по `samtools coverage` — 34.5x.
**Причина:** `samtools stats` по умолчанию считает и дубликаты, а `coverage` и `bcftools mpileup` их пропускают.
**Исправление:** `samtools stats -d`. Теперь все три инструмента описывают одни и те же риды.
**Проверка:** средняя глубина в отчёте <!--ev:mean_depth-->34.5<!--/ev-->x по обоим источникам.

## D-08

**Где:** cwltool + заголовки BAM и VCF.
**Симптом:** записи VCF двух прогонов совпадают, а файлы — нет.
**Причина:** cwltool монтирует входы в случайные каталоги `/var/lib/cwl/stg<uuid>/`. `bcftools mpileup` пишет путь к референсу в `##reference=file://…`, а `bwa-mem2` — свою командную строку с путями в `@PG`.
**Исправление:** входы раскладываются в рабочий каталог шага (`InitialWorkDirRequirement`) и передаются по имени файла. `--no-version` у bcftools и `--no-PG` у samtools убирают командные строки из заголовков. Тест `test_outputs_carry_no_run_specific_paths` следит за этим.
**Проверка:** VCF побайтно одинаковый в <!--ev:repro_comparisons-->10<!--/ev--> сравнениях ([REPRODUCIBILITY](REPRODUCIBILITY.md)); при одинаковом числе потоков совпадает и BAM.

## D-09

**Где:** `scripts/check_reproducibility.sh`, собственный код.
**Симптом 1:** проверка написала «совпадает» для записей VCF и BAM, хотя `docker run` упал.
**Причина 1:** относительный путь в `docker -v` Docker принял за имя тома и отказал. Хеши получились пустыми, а пустая строка равна пустой. Под `set -e` упавшая подстановка команды внутри списка аргументов функции скрипт не останавливает.
**Исправление 1:** абсолютные пути; хеши сначала вычисляются в переменные (там `set -e` срабатывает); пустой хеш — ошибка с кодом 3.
**Симптом 2:** заголовки BAM двух одинаковых прогонов «различаются».
**Причина 2:** `samtools view -H` дописывает в вывод собственную строку `@PG` с путём файла, а пути у двух каталогов разные.
**Исправление 2:** `samtools view --no-PG -H`.
**Проверка:** отрицательные тесты: несуществующий каталог и каталог без BAM дают ненулевой код выхода; два одинаковых прогона дают одинаковый sha256 BAM.

## D-10

**Где:** тестовый Slurm 23.11 и учёт ресурсов.
**Симптом 1:** задача навсегда в `PENDING (InvalidAccount)`.
**Причина 1:** без slurmdbd проверка ассоциаций в 23.11.4 возвращает ошибку (`_refresh_assoc_mgr_qos_list`). Попутная ловушка: `pkill -f slurmd` убивает и `slurmdbd` (совпадает по подстроке), поэтому нужен `pkill -x`.
**Исправление 1:** slurmdbd + MariaDB, кластер, аккаунт и пользователь в `sacctmgr`.
**Симптом 2:** `sacct` показывает для задачи MaxRSS 231 МБ и TotalCPU 4.5 с, хотя шаги внутри заняли до 1.1 ГБ и ~66 CPU-секунд.
**Причина 2:** контейнеры Docker — дети `dockerd`, а не задачи Slurm, поэтому cgroup задачи их не видит. Под Docker Slurm не ограничивает и не учитывает память шагов.
**Вывод:** на HPC нужен Apptainer (контейнер — дочерний процесс задачи в её cgroup), а ресурсы шагов надо мерить изнутри шага (`bin/measure.py`). Это и есть причина [ADR-003](adr/ADR-003-measure-inside-step.md).

## D-11

**Где:** cwltool и Toil.
**Симптом 1:** `cwltool wf.cwl job.yml --threads 2` — `the following arguments are required: --reads_1 …`.
**Причина 1:** cwltool принимает либо job-файл, либо входы в командной строке, но не их смесь.
**Исправление 1:** `scripts/make_job.py` сливает job-файл с переопределениями `key=value` в самодостаточный JSON (пути становятся абсолютными).
**Симптом 2:** Toil со Slurm: `No such file or directory: .toil/js`, затем `exit code 127` у каждой задачи.
**Причина 2:** Toil не создаёт родительский каталог jobStore, а задачи Slurm запускают `_toil_worker` по имени, поэтому venv с Toil должен быть в PATH задачи.
**Исправление 2:** `mkdir -p .toil` и активация venv в `slurm/run_toil_slurm.sbatch`.
**Проверка:** Toil разложил пайплайн на 12 задач Slurm с ресурсами из `ResourceRequirement`, VCF побайтно совпал с cwltool ([slurm_sacct.txt](results/slurm_sacct.txt)).

## D-12

**Где:** `scripts/build_evidence.py`, собственный код.
**Симптом:** в рабочем каталоге `build_evidence.py --verify-source` проходит, а в свежем `git clone` того же коммита сообщает, что `evidence.json` устарел.
**Причина:** хеш исходников считался по всем файлам на диске в `scripts/`, включая неотслеживаемый `scripts/node_modules` (зависимости проверки сайта). В клоне их нет, поэтому хеш другой.
**Исправление:** хешируются только файлы, которые отслеживает git (`git ls-files`); без git — обход каталогов с теми же исключениями, что в `.gitignore`.
**Проверка:** найдено проверкой «как у проверяющего»: клон репозитория, затем тесты, `lint_claims.py`, `check_links.py`, `--verify-source` и сборка сайта. После исправления хеш в клоне и в рабочем каталоге совпадает.

## D-13

**Где:** `docker/tools/Dockerfile`, сборка за прокси, который подменяет TLS-сертификаты.
**Симптом:** первый же `apt-get update` в сборке с `--secret id=extra_ca` падает: `Could not load certificates from /run/secrets/extra_ca (CaInfo option): … Permission denied`, затем `does not have a Release file` для всех трёх репозиториев.
**Причина:** BuildKit монтирует секрет с правами `0400` и владельцем root. `apt` скачивает файлы не от root, а от пользователя `_apt` (песочница `APT::Sandbox::User`), и этот процесс файл прочитать не может. Проверка `[ -s /run/secrets/extra_ca ]` проходит, потому что её выполняет root.
**Исправление:** `RUN --mount=type=secret,id=extra_ca,mode=0444`. Корневой сертификат — открытые данные, читать его можно всем; в слой образа он по-прежнему не попадает.
**Проверка:** чистая сборка за прокси с подменой TLS: `make image EXTRA_CA=…`, тесты htslib <!--ev:htslib_tests_passed-->364<!--/ev--> из <!--ev:htslib_tests_total-->364<!--/ev-->, samtools <!--ev:samtools_tests_passed-->1020<!--/ev--> пройдено и <!--ev:samtools_tests_failed-->0<!--/ev--> ошибок, bcftools <!--ev:bcftools_tests_passed-->2538<!--/ev--> из <!--ev:bcftools_tests_total-->2538<!--/ev-->. Порядок действий — в [OFFLINE](OFFLINE.md).

## D-14

**Где:** проверка сборок bwa-mem2 под разные наборы инструкций ([REPRODUCIBILITY](REPRODUCIBILITY.md#процессор-пять-сборок-bwa-mem2)).
**Симптом:** сборка AVX2, запущенная напрямую (`bwa-mem2.avx2 mem`), дала те же выравнивания и тот же VCF, что прогон через лаунчер на AVX-512, но BAM отличается байтами: в заголовке другая строка `@PG CL:bwa-mem2.avx2 mem …`.
**Причина:** bwa-mem2 пишет в `@PG CL` свою командную строку вместе с `argv[0]`. Лаунчер `bwa-mem2` запускает выбранную сборку с `argv[0] = bwa-mem2`, поэтому в обычном прогоне на любом процессоре в заголовке стоит `bwa-mem2 mem`. При прямом запуске в заголовок попадает имя сборки.
**Исправление:** в `cwl/tools/bwa-mem2-mem.cwl` выбранная сборка запускается как `exec -a bwa-mem2 bwa-mem2.<сборка>`, как это делает лаунчер. По умолчанию (`simd` пустой) команда не меняется. Тест `test_bwa_simd_build_is_chosen_by_the_cpu_unless_forced` следит за обоими случаями.
**Проверка:** сборка AVX-512BW, запущенная напрямую, совпала с прогоном через лаунчер побайтно, включая BAM; так же совпали AVX2, AVX, SSE4.2 и SSE4.1.

## D-15

**Где:** очистка заголовка VCF Strelka2 (`cwl/tools/vcf-clean-header.cwl`), проверка воспроизводимости при 4 и 2 потоках.
**Симптом:** записи VCF и gVCF Strelka2 при 4 и 2 потоках совпали, итоги hap.py тоже, а байты файлов — нет.
**Причина:** шаг, который убирает из заголовка дату и командную строку Strelka2, сам добавлял новую строку: `bcftools view -h` без `--no-version` пишет `##bcftools_viewCommand=view -h /var/lib/cwl/stg…/HG002.strelka2.raw.vcf.gz; Date=…`, то есть случайный путь cwltool и время запуска.
**Исправление:** `bcftools view --no-version -h`. Тест `test_outputs_carry_no_run_specific_paths` теперь проверяет каждый вызов `bcftools view`, `annotate`, `norm` и `concat` во всех CommandLineTool на `--no-version`.
**Проверка:** VCF и gVCF Strelka2, а затем и DeepVariant, побайтно совпали при 4 и 2 потоках ([results/callers](results/callers/reproducibility_strelka2_threads.md)).

## D-16

**Где:** проверка `build_evidence.py --verify-source` в CI.
**Симптом:** локально `--verify-source` проходит, а в CI на том же коммите пишет «evidence.json is stale»; хеши исходников разные.
**Причина:** хеш считался только по файлам, которые git уже отслеживает (`git ls-files`, решение из D-12). `evidence.json` собран до `git add`: новые скрипты, CWL и тесты в хеш не вошли, а в свежем клоне CI они уже отслеживаются.
**Исправление:** хешируются отслеживаемые файлы и неотслеживаемые, но не игнорируемые (`git ls-files --cached --others --exclude-standard`). `node_modules` и кэши по-прежнему вне хеша, а исходник, который забыли закоммитить, по-прежнему даёт расхождение, как и должен.
**Проверка:** тест `tests/test_evidence.py` во временном репозитории: хеш до `git add` и после совпадает, игнорируемые файлы не входят.

## D-17

**Где:** официальный статический бинарник STAR 2.7.11b в образе RNA-seq.
**Симптом:** `objdump -d` находит в бинарнике тысячи инструкций с регистрами `ymm` (AVX, AVX2) и сотни с `zmm` (AVX-512). Если бы они стояли в коде выравнивания, на узле кластера без AVX2 STAR падал бы с SIGILL, а узлы на больших кластерах бывают разных поколений.
**Причина:** Makefile STAR добавляет `-mavx2` (`CXXFLAGS_SIMD`) только к `opal.cpp`. Это SIMD-реализация выравнивания Смита–Уотермана, и вызывается она только из `ClipCR4` — обрезки адаптеров `--clipAdapterType CellRanger4`. Разбор `objdump` по функциям это подтверждает: вне glibc регистры `ymm` и `zmm` встречаются только в `opalSearchDatabase` и шаблонах `searchDatabase*`. Варианты `memcpy`, `strlen` и других функций glibc с AVX-512 выбираются по CPUID во время работы.
**Исправление:** не нужно. Бинарник берётся как есть, а в `docker/rnaseq/Dockerfile` записано, при какой опции ему понадобится AVX2.
**Проверка:** `objdump -d --no-show-raw-insn STAR` с подсчётом `ymm`/`zmm` по функциям; поиск `opal` по исходникам тега 2.7.11b: вызовы только из `ClipCR4.cpp` и `ClipMate_clipChunk.cpp`, через объект `ClipCR4`.

## D-18

**Где:** тесты featureCounts (Subread 2.1.1) при сборке образа RNA-seq.
**Симптом:** скрипты тестов всегда завершаются с кодом 0. Провал проверки виден только по слову `FAILED` в цветном выводе. Заодно `test_corner_cases.sh` начинается с `mkdir -p --countReadPairs result`, и эта команда сама падает: у `mkdir` нет такой опции.
**Причина:** результат проверки печатается, но код выхода не выставляется. Строка с `mkdir` похожа на след массовой замены `-p` на `-p --countReadPairs`, когда в Subread 2.0.2 поменялся подсчёт пар; в том же файле есть и двойной `--countReadPairs --countReadPairs`.
**Исправление:** сборка убирает цветовые коды, считает вердикты PASS и FAILED и падает, если есть хоть один FAILED или нет ни одного PASS. Строка с `mkdir` не мешает: каталог `result` к этому моменту уже создан.
**Проверка:** <!--ev:featurecounts_tests_passed-->52<!--/ev--> проверок пройдено, <!--ev:featurecounts_tests_failed-->0<!--/ev--> провалено ([build_tests.txt](results/rnaseq/build_tests.txt)). На подставных журналах та же логика пропускает сборку только при всех PASS: строка с FAILED или пустой журнал её останавливают.

## D-19

**Где:** `docker/rnaseq/Dockerfile`, загрузка архива Subread с SourceForge за прокси.
**Симптом:** `ADD --checksum=sha256:6392d7c6…` падал с `digest mismatch` четыре раза подряд, и каждый раз полученный хеш был другим. curl на той же машине скачивал файл правильно.
**Причина:** зеркала SourceForge через прокси обрывают передачу: одно сбросило соединение, другое остановилось на 25,7 МБ из 26,1 МБ. `ADD` делает одну попытку и не умеет докачивать, а у обрезанного файла каждый раз своя контрольная сумма.
**Исправление:** архив скачивает `scripts/fetch_source.sh`: повторы, докачка с места обрыва, несколько зеркал по очереди, и файл остаётся, только если сошёлся sha256. Dockerfile берёт его из контекста сборки и сверяет тот же sha256 ещё раз. `make rnaseq-image` и задание GitLab `build:rnaseq-image` делают это сами.
**Проверка:** сборка `make rnaseq-image` за прокси с подменой TLS: архив докачан, sha256 совпал, тесты featureCounts прошли.

## D-20

**Где:** воспроизводимость RNA-seq, повторный прогон с тем же числом потоков.
**Симптом:** счёты, записи BAM и заголовок совпадают, а байты BAM разные. У одного образца в двух прогонах даже разное число блоков BGZF (1 955 и 1 940).
**Причина:** распакованный поток BAM у двух прогонов одинаковый, различаются только границы блоков BGZF. STAR сортирует выравнивания по бинам и сжимает каждый бин отдельно. Границы бинов он выбирает по выравниваниям того потока, который первым заполнил свой буфер (`BAMoutput::coordBins`, под мьютексом), а какие риды окажутся в этом буфере, решает планировщик. Порядок записей от этого не зависит: внутри бина ключ сортировки — позиция и номер рида во входном FASTQ (`BAMbinSortByCoordinate.cpp`).
**Исправление:** шаг `cwl/tools/bam-finalize.cwl`: `samtools view --no-PG -b` записывает тот же поток заново блоками htslib, затем строится индекс. Заголовок остаётся таким, каким его записал STAR.
**Проверка:** повтор на 4 потоках — BAM побайтно одинаковый; 4 против 2 потоков — совпадает всё, кроме заголовка со строкой `--runThreadN` ([отчёты](results/rnaseq/reproducibility_same_threads.md)).

## D-21

**Где:** `cwl/workflows/rnaseq.cwl`, шаг fastp с scatter по образцам.
**Симптом:** шаг упал на сборе выходов: `Did not find output file with glob pattern: ['fastp_["UHR_Rep1", "UHR_Rep2", …].metrics.json']`.
**Причина:** имя шага задавалось как `step_name: {source: samples, valueFrom: "fastp_$(self)"}`. Вход `step_name` не входит в список `scatter`, поэтому `self` в нём — весь массив образцов, а не один образец.

**Проверка:** у каждого образца свой файл метрик (`fastp_UHR_Rep1.metrics.json` и так далее); тест `test_scattered_steps_get_one_metrics_name_per_sample`.

## D-22

**Где:** `scripts/rnaseq_report.py`, собственный код.

## D-23

**Где:** fastp 1.4.0, гистограмма длины вставки в JSON и HTML-отчёте; нашлось при проверке воспроизводимости RNA-seq.
**Симптом:** при 4 и 2 потоках риды после fastp одинаковые, выравнивания и счёты тоже, а «пик длины вставки» у UHR_Rep1 разный: 140 и 154. На одном и том же файле при 1, 2, 3 и 4 потоках пик равен <!--ev:fastp_isize_rna_peak_t1-->145<!--/ev-->, <!--ev:fastp_isize_rna_peak_t2-->154<!--/ev-->, <!--ev:fastp_isize_rna_peak_t3-->161<!--/ev--> и <!--ev:fastp_isize_rna_peak_t4-->140<!--/ev-->.
**Причина:** в гистограмму попадает только часть пар: <!--ev:fastp_isize_rna_evaluated_t1-->227392<!--/ev--> при одном потоке, <!--ev:fastp_isize_rna_evaluated_t2-->114000<!--/ev-->, <!--ev:fastp_isize_rna_evaluated_t3-->76000<!--/ev--> и <!--ev:fastp_isize_rna_evaluated_t4-->57000<!--/ev--> при двух, трёх и четырёх. fastp читает риды пачками по 1000 пар и раздаёт пачки рабочим потокам по кругу, а длину вставки считает только поток 0: в `src/peprocessor.cpp` прямо написано `// we only use thread 0 to evaluate ISIZE`. С N потоками гистограмма строится по каждой N-й пачке, и состав этой выборки зависит от N. В документации fastp об этом не сказано. На WGS тот же эффект: в эталонном отчёте на 4 потоках стоял пик <!--ev:fastp_isize_wgs_peak_t4-->264<!--/ev--> вместо <!--ev:fastp_isize_wgs_patched_peak-->261<!--/ev--> по всем парам.
**Исправление:**
1. В отчётах этот пик больше не используется. Длина вставки берётся из `samtools stats` по всем парам (WGS), а в отчёт RNA-seq она не входит. Эталонный отчёт WGS пересобран из тех же выходов прогона: изменились только эта строка и время сборки.
2. Для fastp написан патч из трёх строк (`docker/fastp-isize/fastp-1.4.0-isize-all-threads.patch`). Гистограмма в fastp и так атомарная (`atomic_long`), а перекрытие пары при обрезке адаптеров уже считается в каждом потоке, поэтому можно просто вызывать `statInsertSize` во всех потоках. Пайплайн по-прежнему использует официальный бинарник; патч — предложение для апстрима.
**Проверка:** `make fastp-isize-image fastp-isize` собирает fastp из тега v1.4.0 дважды, как есть и с патчем, и гоняет обе сборки и официальный бинарник на 1–4 потоках на RNA-seq и WGS ([таблица](results/fastp_isize_threads.md)). Сборка из тега совпадает с официальным бинарником при любом числе потоков (<!--ev:fastp_isize_release_matches_official-->да<!--/ev-->). У исправленной гистограмма одна и та же при любом числе потоков и равна однопоточной (<!--ev:fastp_isize_patched_thread_independent-->да<!--/ev-->). Риды на выходе одинаковые во всех прогонах (<!--ev:fastp_isize_reads_identical-->да<!--/ev-->). Тесты `tests/test_fastp_isize.py` держат эти свойства и модель «поток 0 видит каждую N-ю пачку».
